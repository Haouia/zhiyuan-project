## 2. 受众、目标与成功标准

**受众**：评委 / 企业技术负责人 / 业务负责人 / HR 信息化同事。多数人听过 RAG，但被“Demo 很惊艳、上线不敢用”坑过。

**目标（按优先级）**
1. 让听众在 1 分钟内理解“这个系统解决什么具体问题”——年终制度问答，而不是又一个聊天框。
2. 让听众相信“**敢用**”：答案有出处、资料不足会拒答、有金标评测和门禁、有权限边界、有故障预案。
3. 让听众记住四个词：**可信、可度量、可控、可运营**——四个支柱就是全部叙事骨架。
4. 现场演示可复现：8 步走完，每步都有“现场该看什么”，失败有兜底。

**成功标准（可自检）**
- 讲完能被复述一句话：“把能跑通的 RAG Demo，做成企业敢用的知识引擎。”
- 至少 3 个具体证据被记住：引用逐字回查、0.967/0.967 过 0.90/0.85 门禁、双租户 403/404。
- 15 分钟不超时；演示页 8 步在 3 分钟内完成。

## 3. 叙事结构：三幕 + 一条证据链

```
第一幕 为什么（1 分钟）        S2 痛点：制度在那里，员工却问不到
第二幕 是什么（约 7.5 分钟）    S3 定位 → S4 架构总览 → S5 写入链路 → S6 问答链路
                              → S7–S10 四支柱（可信/可度量/可控/可运营）
第三幕 怎么证明（约 6.5 分钟）  S11 现场演示 8 步 → S12 证据链 → S13 工程化 → S14 收尾
                              S15–S21 附录（深挖 4 题 + Q&A + 速查 + 清单，备用不主动翻）
```

**为什么这样排**
- 痛点用“入职满一年能休几天年假？旧版 7 天、新版 9 天”这个真实冲突开场，比讲技术栈更快建立代入感。
- 架构页**只给全景和五个落点**，细节留给后两页放大；避免在 15 分钟里讲 13 个容器。
- 四支柱按“听众关心顺序”排：可信（敢不敢用）→ 可度量（好不好）→ 可控（谁能用）→ 可运营（挂了怎么办）。
- 证据链放在演示之后：先让听众看到真实页面，再用“契约/冒烟/E2E/五阶段/verify_release”解释“不是演给你看的”。
- 附录是“被追问时的弹药库”，不占主线时间。

## 5. 审美定位（Aesthetic Positioning）

### 5.1 结论：纸 · 墨 · 靛蓝

| 关键词 | 含义 | 落到画面上 |
|---|---|---|
| 纸（Paper） | 企业制度、文档、可回查的原文 | 底色 `#F6F5F1`，不用纯白；正文像印在纸上 |
| 墨（Ink） | 正文、结论、可引用的句子 | 标题与强调 `#15171C`；二级 `#4C525B`；发丝线 `#E6E3DB` |
| 靛蓝（Indigo） | 产品主色、引用角标、交互 | 强调 `#3948D4`，浅底 `#EDEFFC`；与 `admin-web` UI 同源 |

### 5.2 为什么是这套（审美区域定位）

项目的“审美锚点”不是炫技，而是**证据**：
1. **产品本身就是纸墨风**：`admin-web/src/style.css` 的设计令牌就是 paper/ink/accent 三色系，界面是浅色文档库 + 靛蓝按钮。PPT 沿用同一套令牌，演示时 PPT 与系统界面“看起来是一个东西”，可信度直接提升。
2. **业务对象是制度文档**：制度＝纸，正文＝墨，引用＝靛蓝角标。因此“纸底色 + 深墨标题 + 靛蓝引用/数字”不是装饰选择，而是内容语义的视觉翻译。
3. **评审场景需要克制**：深色赛博、渐变紫、玻璃拟态会让“企业敢用”的说服力打折；纸墨风更接近审计、法务、HR 的语感。
4. **证据优先的版式**：截图与架构图一律加 1px 发丝边框 + 轻阴影，像“贴在纸面上的附件”，让听众先看证据、再看结论。

**四个审美区域**（不同页面用不同“质感”）：
- 品牌区（S1/S3/S14）：深墨底 `#101318`，大字宣言，占满版心——负责“记住”。
- 纸面区（S2/S5–S13/S15–S21）：纸色底，信息密集、发丝线分隔——负责“讲清楚”。
- 镶嵌区（S7–S10 的截图）：白卡 + 细边框 + 轻阴影，像贴在纸上的系统截图——负责“证明是真的”。
- 工具区（S19–S21 附录）：更小字号、表格/清单化——负责“被追问时查得到”。

### 5.3 明确不做的
- 不用未授权的第三方图片/插画；全部图形为原生形状或项目自有截图/架构图。
- 不用高饱和撞色、荧光色；强调色全稿不超过 3 种（靛蓝、成功绿、警告琥珀）。
- 不用“一页 6 个要点 + 小图标堆”的模板感；每页只留一个主张。
- 正文不用纯黑 `#000`，用墨色 `#15171C`，降低投影眩光。

## 6. 视觉系统规范

### 6.1 画布与栅格
- 16:9，13.333 × 7.5 英寸（1280 × 720 pt 逻辑尺寸）。
- 左右页边距 `0.62"`，页眉基线 `0.62"`，页脚基线 `7.20"`。
- 内容区宽 12.09"；常用分栏：对半 5.85/5.85、三七 5.90/6.19、四栏 2.86×4 + 0.16 间距。
- 卡片圆角 0.10"（约 7px），chip 圆角 0.07"；线宽：发丝线 0.75pt，强调线 1.2–1.5pt。

### 6.2 字体层级

| 用途 | 字体 | 字号 | 颜色 |
|---|---|---|---|
| 大标题 | Microsoft YaHei UI Bold + Segoe UI Variable Display | 37–40pt | ink |
| 副标题/导语 | Microsoft YaHei UI | 12.5pt | ink2 |
| 卡片标题 | Microsoft YaHei UI Bold | 10.5–12pt | ink |
| 正文/说明 | Microsoft YaHei UI | 8.5–9.6pt | ink2 |
| 眉标（章节号/英文） | Cascadia Mono | 8pt，字距 +1.0 | ink3 / 支柱色 |
| 数字与大写代号 | Cascadia Mono Bold | 17–34pt | ink / 支柱色 |
| 代码、端口、指标名 | Cascadia Mono | 8–8.6pt | info |

> 演示机若无 `Segoe UI Variable Display`，PowerPoint 会回退到 Segoe UI，观感基本一致；**Cascadia Mono 缺失时**回退等宽字体，数字仍对齐。绝对不要换成宋体/黑体混排。

### 6.3 色板（与产品 1:1）

| 令牌 | Hex | 用途 |
|---|---|---|
| paper | `#F6F5F1` | 浅色页背景 |
| paper-2 | `#EFEEE8` | 浅灰卡片底 |
| surface | `#FFFFFF` | 内容卡片 |
| ink | `#15171C` | 标题/主文字 |
| ink-2 | `#4C525B` | 正文 |
| ink-3 | `#6C727A` | 注释/眉标 |
| line / line-strong | `#E6E3DB` / `#D8D4CA` | 发丝线、chip 边框 |
| accent | `#3948D4` | 强调色、可度量支柱 |
| accent-ink | `#2A36A8` | 浅底上的强调文字 |
| accent-soft | `#EDEFFC` | callout 底色 |
| success | `#0E7355` | 可信支柱、通过/达标 |
| warning | `#9A5B09` | 可运营支柱、风险提示 |
| info | `#29527A` | 平台/信息蓝灰、可控支柱 |
| sidebar/dark | `#101318` | 深色品牌页、页脚深色卡 |
| dark-card / dark-line / dark-muted | `#171B22` / `#2A2F38` / `#9DA3AE` | 深色页内卡片与次级文字 |

**语义固定**：绿=通过/可信，靛蓝=可度量/引用，蓝灰=可控/平台，琥珀=可运营/警告，红 `#B02A37` 只用于门禁阈值线与“不通过”。跨页不换色，听众才能把颜色当索引。

### 6.4 组件库（见 `deck_kit.py`）
- **页眉**：眉标（章节号 + 中文小标，mono）→ 标题（一句话主张）→ 导语（一句话解释）。
- **页脚**：左“知源 · 企业级 RAG 知识平台”，右“NN / 21”。
- **证据框 `evidence()`**：图片 + 0.75pt `line` 边框 + 轻阴影 + mono 图注（图注写“看到了什么”，不写“截图”）。
- **callout**：浅靛蓝底 + 深靛蓝粗体一句话，全稿每页至多 1 个，只放“可讲的一句”。
- **chip / 状态机 / 时间轴 / 角色卡**：只用圆角矩形 + mono 文本，不引入图标包。
- **深色页**：`#101318` 底 + `#171B22` 卡 + `#2A2F38` 线；彩色只留靛蓝亮色 `#8C97F2` 做强调。

## 7. 逐页规划（21 页）

> “这一页要证明什么”是设计依据；“讲解要点”与 PPT 备注同源，备注里还有逐页 1–2 句口播。

| # | 章节 | 标题 | 这一页要证明什么 | 视觉构成 | 讲解要点 | 时长 |
|---|---|---|---|---|---|---|
| 01 | 封面 | 让员工问制度，像问一位熟悉的 HR | 一句话说清产品与对象 | 品牌标 + 大标题 + 四支柱 chip + 右侧 SPEC 深色卡（13 容器/40 题/10 服务/9 指标） | 不念目录；开场句用标题；SPEC 卡留给提问时指 | 0:30 |
| 02 | 为什么 | 制度就在那里，员工却问不到 | 痛点真实、具体、可感 | 左“年假问题”场景卡（7 天 vs 9 天）+ 右侧四条痛点 + 底部结论句 | 讲 HR 群里的真实冲突；停在“答案取决于谁先回复” | 1:00 |
| 03 | 定位 | 把能跑通的 RAG Demo，做成企业敢用的知识引擎 | 主张 + 四支柱 = 全篇骨架 | 深色品牌页：标题 + 管理员上传→员工提问→答案带引用三步闭环 + 四支柱（各带“详见 07–10”指路） | 只读标题句与四个词；说明后面按四支柱展开 | 1:00 |
| 04 | 架构 | 一条链路，五个落点 | 系统有边界、有分层、不是黑盒 | 全链路图（7.62" 宽）+ 右侧 ACCESS/EDGE/WRITE/QUERY/GOVERN 五层注解 | 只讲“两条主链 + 共用网关与治理”；不念框内小字 | 1:00 |
| 05 | 写入 | 一份文档，怎样变成“可被引用”的版本 | 异步、可回滚、失败不伤线上 | 5 卡流程（上传/解析/事件/索引/生效）+ 状态机（PENDING→…→READY，任一失败→FAILED）+ 3 张事实卡 | 强调 202 即返回、分块数核验才推进 activeVersion、旧版不被覆盖 | 1:00 |
| 06 | 问答 | 一句提问，十步之内必有出处 | 检索→生成→校验的闭环与退路 | 5 卡（提问/检索/生成/引文校验/答案）+ 40s/20s/1 次三个大数字 + 四种结果码卡 | 先讲“先保证不出错，再追求答得好”；引文校验失败 502 不落地 | 1:00 |
| 07 | 支柱一 可信 | 可信不是形容词，是一条能回查的链路 | 引用可点、可回原文、可拒答 | 左：问答答案截图 + 引用抽屉截图；右：四条要求（本次召回/逐字命中/资料不足拒答/502 失败） + 底部绿 callout | 现场点开角标回查；讲“宁可得不到答案，也不给看起来对的答案” | 1:00 |
| 08 | 支柱二 可度量 | 答得好不好，用分数说话 | 有金标、有门禁、有报告 | 4 张 KPI 卡（40 题/0.90-0.85/0.967-0.967/38-41）+ 评测页截图 + 双门禁进度条 + 三条工程化小注 | 讲 40 题构成与两条门禁线；0.967/0.967 是 30 道有答案题口径 | 1:00 |
| 09 | 支柱三 可控 | 谁能上传、谁能提问、谁不能越界 | 身份来自企业、权限有边界、注册有门槛 | 左：用户与权限页截图 + 管理员/成员角色卡；右：身份/边界/角色/入口四条 + 底部邀请码→注册→晋升→重登流程 | 强调账号不归本系统管（Keycloak）；403/404/400/409 是验收过的 | 1:00 |
| 10 | 支柱四 可运营 | 故障不是意外，是预案 | 每类故障都有动作和指标 | 左：系统监控页截图 + 10/10、9 项两个大数字；右：主备/限流/计量/对账四卡 + 6 个 Prometheus 指标名 | 四类故障各一句；强调监控页本身抗故障（单探测失败不拖整页） | 1:00 |
| 11 | 现场演示 | 8 步，3 分钟，把四个支柱走一遍 | 脚本可执行、失败有兜底 | 深色表头的 8 行表格：步骤/操作/现场看什么/对应支柱，行左色条按支柱着色；底部“兜底”一行 | 按表走；每步只说“看什么”；失败就切录屏 | 3:00 |
| 12 | 怎么证明 | 证据不在 PPT 里，在流水线里 | 可重复执行，不是“我测过了” | 6 张证据卡（契约 20+10=30 / API 冒烟 268 / E2E 28+22+15+19 / 五阶段 / verify_release 7 步 / 不可变镜像）+ 底部四个大数字 | 讲“本地一条命令与 CI 同源”；数字念大数即可 | 1:30 |
| 13 | 工程化 | 13 个容器，一条命令起停 | 演示环境就是交付形态 | 13 个容器 chip（与 compose 一一对应）+ 左“版本锁定”、右“发布与观测”两列 + 底部文件清单 | 讲版本锁定、镜像不可变、K8s 三类探针；不说“K8s 里 13 个容器” | 1:30 |

## 14. 迭代与维护说明

1. **改数字**：先改 `fact-pack.md` 的记录，再改 pptx（或运行 `patch_facts.py` 的同构替换），最后检查 S8/S12/S13 三页。

5. **版本记录**：本稿 v1.0（2026-11-25）完成 21 页、备注全量、事实校正；下一版若要改定位（如面向外部客户），先改 S2/S3 的受众假设与 S12 的证据口径。
